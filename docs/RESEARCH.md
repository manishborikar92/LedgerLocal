Every claim below is tagged **[verified]** (seen on a source named here), **[vendor claim]**, **[secondary]** (third-party article), or **[unverified]**. ## 1. What the research changed
* The market already has local/offline converters and tools that check statements against printed balances. LedgerLocal therefore does **not** claim that reconciliation or local processing is unique. Its angle: processing that is *enforced* (strict CSP, tested), a clickable PDF-to-row audit trail, a row-by-row running-balance check, native QBO/OFX, and no page limits.
* A previously cited "~83% accuracy for rule-based converters" figure could not be verified and is not used anywhere. All accuracy numbers are our own and labelled "on synthetic layouts".
* The product is **client-first**: no accounts, no database and no separately hosted backend. A Next.js server renders pages and a theme cookie, and never receives statement data; processing happens in the browser.

## 2. Landscape (features only)
* **Cloud tools** (e.g. DocuClipper) export Excel, CSV, QBO, IIF, OFX, QFX and QIF and advertise an automatic reconciliation check ([feature page](https://www.docuclipper.com/pricing), [comparison page](https://www.docuclipper.com/comparisons/quickbooks-pdf-import-alternative/)) [vendor claims]. They upload files to their servers.
* **Local / offline tools**: a Windows desktop converter with CSV/Excel/QBO export, OCR and "every row verified against printed balances" ([AlternativeTo](https://alternativeto.net/software/offline-bank-statement-converter/about/)) [listing/vendor claim]; browser-based tools that process locally but export CSV only ([Capterra listing](https://www.capterra.com/p/10049899/Bank-Converter/), [another](https://karlgusta.gumroad.com/l/yxufpx)) [listing/vendor claims].
* **Complaints that shaped the design** (practitioner articles; Reddit threads could not be retrieved in this session) [secondary]: silently wrong signs and dropped rows ([DEV article](https://dev.to/christian_rousseau_c6a94f/how-to-convert-bank-statement-pdfs-to-csv-for-quickbooks-xero-2026-3kcl), [StatementDecoder](https://statementdecoder-web.onrender.com/blog/import-bank-statements-into-quickbooks)); DD/MM vs MM/DD mix-ups; balance mismatches; LLM "hallucinated" rows. → sign convention surfaced and checked by reconciliation; date order detected from evidence and disclosed; deterministic parser (no ML guessing).

## 3. Real statement layouts
From practitioner descriptions above and general knowledge of US/UK/EU/Indian statements [secondary / own knowledge, not a systematic survey]:
* **Bank**: signed single "Amount" column; or separate Withdrawals/Deposits (Debit/Credit, Paid out/Paid in, Money out/in) columns; running "Balance" column on every line or only per day; "Balance brought forward / carried forward" rows (UK); a summary box (Beginning balance, Deposits, Withdrawals, Ending balance) that must not be mistaken for transactions; "Daily balance" tables with dates and balances only (decoys); multi-line descriptions; repeated headers and footers per page; table continuing across pages; dates without a year ("Dec 28") across a Dec→Jan period.
* **Credit card**: Previous balance + purchases − payments = New balance; payments shown as negatives or with `CR`; two date columns (transaction/post); separate "Payments and credits" and "Purchases" sections each with their own header and total.
* **Other formats**: parentheses negatives `(45.00)`, trailing minus `45.00-`, `CR`/`DR` suffixes, European `1.234,56` with `DD.MM.YYYY`, Indian lakh grouping `1,23,456.78` with `DD-MM-YYYY`.
These shaped the 15 synthetic layouts in `tools/synth` (see DESIGN.md §9 and ACCURACY.md).

## 4. OFX 1.x and Intuit Web Connect (.QBO)
Sources: ProperSoft's [QBO format notes](https://www.propersoft.net/howto/qbo-format-web-connect-format/), [QuickBooks Desktop import guide](https://www.propersoft.net/import-qbo-quickbooks/), [DancingNumbers: "Unable to verify the financial institution"](https://www.dancingnumbers.com/unable-to-verify-the-financial-institution/), plus open-source OFX libraries and documentation consulted for field conventions. **Intuit's own Web Connect specification is behind a developer login and was not retrievable → [unverified] against the primary source.** What the writer implements and why:
* QBO is an OFX file with an extra `INTU.BID` element inside `SONRS` identifying the financial institution [secondary]; plain OFX has none. QuickBooks Desktop can refuse files whose institution it cannot verify [secondary]. → `INTU.BID` (default `3000`, a generic placeholder; **not verified against Intuit's directory**) is user-configurable and the README documents the failure mode.
* OFX 1.0.2 SGML: header lines (`OFXHEADER:100`, `DATA:OFXSGML`, `VERSION:102`, …), aggregates closed, leaf elements unclosed, ASCII text with `&`, `<`, `>` escaped. → implemented and **parsed back by the independent Python `ofxparse` library** in the test-suite.
* Bank statements use `BANKMSGSRSV1/STMTTRNRS/STMTRS` with `BANKACCTFROM` (BANKID, ACCTID, ACCTTYPE); cards use `CREDITCARDMSGSRSV1/CCSTMTTRNRS/CCSTMTRS` with `CCACCTFROM`. Debits carry negative `TRNAMT`; for a card the ledger balance is the amount *owed* as a negative number.
* `FITID` must be unique per account so importers can skip already-imported items; `NAME` ≤ 32 characters and `MEMO` ≤ 255 in OFX 1.x (field sizes from the OFX 1.x specification as commonly documented; not re-read from ofx.net in this session). → FITID = `LL` + 22 hex chars of SHA-256(account | date | amount | original description | repeat counter) = 24 characters; NAME truncated to 32 with the full text in MEMO.
* Dates: `YYYYMMDD120000[0:GMT]` (noon GMT avoids time-zone date shifts).
* **Not tested here**: importing into real QuickBooks Desktop/Online or Xero (no access). The README says so prominently.

## 5. How QuickBooks and Xero take imports
QuickBooks Desktop: Web Connect (`.qbo`) via File → Utilities → Import ([ProperSoft](https://help.propersoft.net/article/502-import-qbo-quickbooks)); QuickBooks Online: an upload-transactions flow accepting QBO/OFX/CSV ([DancingNumbers](https://www.dancingnumbers.com/import-bank-statements-into-quickbooks-online/)); Xero: import-a-statement accepting OFX/QIF/CSV, QBO per [ProperSoft](https://help.propersoft.net/article/487-import-file-xero) [secondary]. CSV import in both needs a specific column layout (date, amount or debit/credit, description) → the CSV exporter has configurable columns, date formats, signed vs debit/credit and decimal mark. Menu names change between versions; the README tells users to check vendors' current help.

## 6. Stack versions and practices (npm registry, 21 Oct 2026; dependencies updated 22–24 Nov 2026)
Next.js 16.4.6, React 19.3.1, Tailwind 4.3.5, pdfjs-dist 6.5.438, zod 4.6.7, Vitest 5.1.1, idb 8.0.4, @tanstack/react-virtual 3.14.26 (a week-old release on purpose, D-26), fflate 0.8.3, @noble/hashes 2.4.0, pdfkit 0.21.0, Playwright 1.65.1. Deviations: **TypeScript 5.9.3** (TS 7 is the `latest` tag but a native rewrite whose compatibility with Next/typescript-eslint/Vitest was not established); **ESLint 9** (eslint-plugin-jsx-a11y does not yet declare ESLint 10 support).

**pdf.js 6 — findings from running it (not from docs):**
* The modern build calls `Map.prototype.getOrInsertComputed`, missing from Chromium 141 → page *rendering* failed; the **legacy build** carries polyfills. That was the reason for using the legacy build until November 2026. Since then: browser support for those APIs is Chrome/Edge 145, Firefox 144, Safari/iOS 26.2 ([caniuse](https://caniuse.com/mdn-javascript_builtins_map_getorinsertcomputed); Baseline "newly available" since 2026-02-14), so the browser bundle now uses the modern build and the legacy build remains only for Node, where pdf.js prints "Please use the `legacy` build in Node.js environments" and Node 22 lacks `getOrInsertComputed`, `Promise.try` and `Uint8Array.fromBase64`. Measured in Chromium 153 by removing each API before the page loaded (page realm) or by patching the worker scripts in flight (worker realms), for the sample statement. With pdfjs-dist 6.5.438: all four of `getOrInsert*`, `Promise.withResolvers`, `Promise.try` and `Uint8Array.prototype.toHex`/`fromHex` are required on the main thread; the workers need `Promise.try`, `toHex`/`fromHex` and `Promise.withResolvers` but not `getOrInsert*`; nine other recent features (base64 helpers, `Math.sumPrecise`, `URL.parse`, `Array.fromAsync`, iterator helpers, Set methods, `Error.isError`, `RegExp.escape`, Float16) removed together change nothing. With 6.4.299 the split was different (the page needed only `getOrInsert*` and `withResolvers`, the workers `Promise.try` and `toHex`), so the realm distribution can shift between versions; `tools/check-browser-support.mjs` repeats the experiment.
* `isEvalSupported` no longer exists (no eval fallback path) — consistent with a [community note](https://github.com/wojtekmaj/react-pdf/discussions/1786) that the option is gone in 6.x.
* Parsing in our own Web Worker works with pdf.js's in-thread "fake worker" (`globalThis.pdfjsWorker`), avoiding nested workers; main-thread rendering uses pdf.js's own worker, referenced with `new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url)` so webpack emits it as a hashed asset on our origin.
* pdf.js emits blank spacer items (zero height) between text runs; the geometry layer drops them.
* Standard-font and cMap files are fetched with `fetch` → blocked by `connect-src 'none'`; pdf.js falls back to system fonts. Visual fidelity of non-embedded fonts in the preview is lower, text extraction is unaffected. JPEG 2000/ICC (WASM) images do not render in the preview for the same reason.

**Strict CSP on a server-rendered app:** a per-request nonce (generated in `src/proxy.ts`, applied by Next.js to its own scripts, with `'strict-dynamic'` for the chunks they load) replaces hashing inline scripts, and forces dynamic rendering (`await connection()`). Policy per route: the workbench gets `connect-src 'none'` and `form-action 'none'`, other pages their own origin only (DESIGN.md §2.1). Measured pitfalls found by testing: (a) zod 4's JIT uses `new Function` → CSP violation until `z.config({ jitless: true })`; (b) a service worker inherits the CSP of its own script response, so `/sw.js` must **not** receive the document policy (it would block the precache fetches); (c) Turbopack's worker loader keeps its bootstrap config in the URL fragment, which a cache-served response cannot preserve → the production build uses **webpack**, and since Next.js 16 refuses to run Turbopack when a `webpack` config exists, `dev` uses webpack too; (d) `Referrer-Policy: no-referrer` makes browsers send `Origin: null` on same-origin form posts, which Next.js rejects for Server Actions → `same-origin`; (e) entering the workbench with `next/link` would keep the previous page's weaker policy → a plain `<a>`.

**Service worker on a server-rendered app:** there is no static file list, so the build emits one (`/_next/static/ll-precache.json`, from a webpack plugin) and the worker caches it at install together with the `/app/` document and its CSP header, the pdf.js worker and icons; it refreshes the cache when an online visit shows a new build (DESIGN.md §2.1). Verified in Chromium: Cache Storage holds every listed file, and a reload with the network disabled still reconciles a statement.

### 9.2 Colour and status [source]
* WCAG 2.2 **1.4.1 Use of Color**: colour must not be the only visual means of conveying information ([Understanding SC 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)). Every status here has a glyph or a line style as well as colour (✓/✗/– in the tick margin, the stamp's wording, outline styles on the PDF).
* **1.4.11 Non-text Contrast**: user-interface components and graphical objects need 3:1 against adjacent colours, and thin lines should be avoided or exceed the minimum because anti-aliasing lowers the effective contrast ([Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast)). Consequence: control borders use a 3:1 token (`--border-strong`), PDF outlines are at least 1 px and drawn in colours measured against white paper, and decorative hairlines use a separate lighter token that carries no information.
* Stripe documents building its palette in a perceptually uniform colour space so that equal lightness gives equal contrast across hues ([Designing accessible color systems](https://stripe.com/blog/accessible-color-systems)); Linear describes deriving themes from a few variables (base, accent, contrast) in LCH rather than hand-tuning 98 values ([How we redesigned the Linear UI](https://linear.app/blog/how-we-redesigned-the-linear-ui)). Consequence here: the palette is authored in OKLCH, shipped as hex pairs inside `light-dark()`, and *measured* (`tools/check-contrast.ts`, a Vitest guard) rather than trusted. [Both pages were read as search excerpts, not in full.]

### 9.3 Data-table density [source]
IBM Carbon's data-table style page defines five row heights (24, 32, 40, 48, 64 px), says the header row should match the row size, recommends the densest sizes "for highly dense layouts where maximizing information within limited space is a priority", and says row hover should always be enabled because it helps scanning even when rows are not interactive ([style](https://carbondesignsystem.com/components/data-table/style), [usage](https://carbondesignsystem.com/components/data-table/usage/)). Consequence: 32 px rows with hover for fine pointers (the old rows were 36 px); 44 px for coarse pointers, above the WCAG 2.5.8 24 px minimum cited in AUDIT.md §2; a taller two-line row in narrow panes instead of squeezing four columns into 370 px.

### 9.4 Split panes [source]
The W3C ARIA Authoring Practices **window splitter** pattern: a focusable `separator` with `aria-valuenow`/`min`/`max`, `aria-controls` pointing at the primary pane, arrow keys moving it, Home/End jumping to the extremes (optional) and Enter collapsing (optional) ([APG](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter)). The old splitter lacked `aria-controls` and Home/End; both were added. Enter-to-collapse was not (the pane range is 25–75%).
