# Production-quality audit

Scope: Next.js/Vercel best practices, SEO and social sharing, performance, accessibility, security, content accuracy for a **client-first** app, a full visual redesign, a code-quality pass (v2, 24 October 2026), and the migration to a standard Next.js 16 **server** architecture (this version, 22 November 2026). Evidence tags as in [RESEARCH.md](RESEARCH.md): **[verified]** = measured or run here; **[source]** = taken from a cited page; **[unverified]** = not confirmed.

## 1. Method
Research first (web search), then a baseline review of the v1 code, then changes, each verified with tests, the production build, real-Chromium E2E and Lighthouse. Visual review used screenshots of every key screen in both themes and a phone viewport; it found three layout bugs no test had (§4). The server migration was verified by re-running everything against `next start` and by checking the failure modes it introduced (§4b).

## 3. Content audit (accuracy for a free, client-first tool)
Copy was reviewed so that every claim is true of the product: no unverified third-party claims, only measured numbers (always with the synthetic-data caveat), a visible "Not financial advice" notice. A test fails if app source contains commerce or separate-backend vocabulary, and E2E checks every rendered page for it. Two statements became inaccurate when a Next.js server was introduced and were corrected: the FAQ no longer says there are no servers (it says nothing about your statements ever reaches one), and the verify-offline guide and landing card now name the workbench page (`/app/`) as the one whose policy is `connect-src 'none'`, with the policy read from the response headers rather than the page source. The project is MIT-licensed (D-19).

## 4b. Findings and fixes (server migration, 22 November 2026) [all verified here]
| # | Area | Finding | Fix | Evidence |
|---|---|---|---|---|
| 10 | Offline | **Offline reload of the workbench failed**: the service worker cached the HTML and the chunks the HTML names, but not the lazily loaded ones (workbench, dialogs, export engine, parse worker, pdf.js renderer); one such chunk returned `ERR_FAILED` offline. | A webpack plugin emits `/_next/static/ll-precache.json`; the worker caches it at install, off the main thread (no module is executed to warm the cache). Install fails unless everything cached, so "Ready offline" is truthful. | Offline E2E now also asserts Cache Storage holds all 43 listed build files; it fails against the old worker (35 chunks missing) and passes against the new one. |
| 11 | Offline | `sw.js` is a static file, so browsers would not re-install it for a new deploy and an install-time cache would go stale after the first release. | The worker re-precaches when an online `/app/` load shows a changed asset set, keeps one previous generation and prunes older files. | Three consecutive real builds, one browser profile: the cache equalled the newest two builds' files, and the changed lazy dialog rendered from cache with the server stopped and the network off (manual, one-off script, not in the suite). |
| 12 | Developer workflow | **`npm run dev` failed** after the precache plugin was added: Next.js 16 runs dev under Turbopack and refuses to start when a `webpack` config exists. | `dev` is `next dev --webpack`, like `build`; a hygiene test asserts both flags. | Dev smoke test: the workbench reached RECONCILED with no CSP violations. |
| 13 | Dependencies | `npm audit` flagged Next.js 16.4.2 (moderate). | Next.js 16.4.6; `engines.node` corrected to `>=22.13.0` (pdfjs-dist 6 requires it; it said `>=20.9.0`). | `npm audit`: 0 vulnerabilities. |
| 14 | Accuracy of copy | FAQ said "no servers"; a guide said production pages declare `connect-src 'none'` and could be read in the page source. | Reworded (§3). | Source review; E2E content tests pass. |
| 15 | Code quality | React warned in dev about a `key` inside a spread props object in `Grid.tsx`. | `key` passed explicitly on each cell. | Dev console is now empty. |
| 16 | Tooling | The previous bundle-report tool did not apply to the server build, and the Lighthouse runs were not reproducible. | `tools/bundle-report.mjs` and `tools/lighthouse.mjs`, with the Lighthouse and Chrome versions recorded in the output. | `docs/bundle-report.json`, `docs/lighthouse.json` |
| 17 | Security | The security headers, per-request nonces and per-route policies were untested on the server build. | `e2e/server.spec.ts` (6 tests), `tests/unit/csp-architecture.test.ts`. | all pass |

## 5. Measurements (production build via `next start`, Chrome 153, single-core sandbox) [verified]
**Lighthouse 13.6.0** ([docs/lighthouse.json](lighthouse.json)); median of 3 runs; Lighthouse's host benchmark index about 1,400:
| Page | Perf mobile (slow 4G, 4× CPU) | Perf desktop | A11y | Best practices | SEO | Mobile LCP / TBT / CLS (median) |
|---|---:|---:|---:|---:|---:|---|
| Landing | 86 (runs 82, 87, 86) | 100 | 100 | 100 | 100 | 0.93 s / 573 ms / 0 |
| Guide | 83 (82, 83, 89) | 100 | 100 | 100 | 100 | 0.77 s / 692 ms / 0 |
| Workbench `/app/` | 85 (87, 85, 84) | 100 | 100 | 100 | n/a (`noindex`) | 0.82 s / 578 ms / 0 |
* The handover target of roughly 90+ for the workbench on mobile was **not reached on this host**. The landing page, a server component with a tiny client island, shows the same Total Blocking Time as the workbench, and the main-thread cost is dominated by the React/Next.js client runtime chunk (about 640 ms scripted at 4× slowdown in one inspected run). That points to a runtime floor on this machine rather than workbench code; it is an inference, not a tested cause. The service-worker precache does not appear in the load measurements (it starts after load and idle), and the 1.2 MB pdf.js chunk is not requested at load.
* Lighthouse 12.8 on the same build and Chrome (two runs each, not recorded in the JSON) scored lower: landing 76–77, workbench 77–82. Scores from earlier versions of the app, measured with a different Lighthouse and Chromium, are not comparable and are not reused. Variance between runs is several points.
* SEO is 100 on indexable pages. In the earlier build it was 92 because the global `connect-src 'none'` blocked Lighthouse's `robots.txt` audit; only the workbench has that policy now.
**Bundles (gzip)** ([docs/bundle-report.json](bundle-report.json)): landing ≈ 169 KB JS + 9 KB CSS; workbench shell ≈ 212 KB JS; loaded on use: parse worker ≈ 370 KB, PDF renderer ≈ 144 KB, pdf.js render worker ≈ 383 KB. Offline install: 44 files, ≈ 1.4 MB gzip (4.4 MB raw).
**100-page, 4,300-row statement:** file → RECONCILED in ≈ 4.1 s in the browser worker including the first on-demand load of the workbench; max main-thread frame latency 104 ms, 7 long tasks over 50 ms, longest 171 ms ([docs/perf-browser.json](perf-browser.json)). Node: 2.1 s extract + 0.38 s parse ([docs/perf-node.json](perf-node.json)).
**Tests:** 158 Vitest (unit, contract, integration incl. `ofxparse`/`openpyxl`/LibreOffice, architecture/CSP/hygiene guards) + 25 Playwright.

## 6. Not verified
* No real Vercel, Render or Coolify deployment was made; `NEXT_PUBLIC_BASE_PATH` sub-path hosting and a reverse proxy in front of the server (Server Action origin check) were not tested. The `?dpl=` deployment-id query that Vercel can add to asset URLs is handled by the service worker (matching ignores the query) but that was not tested on Vercel.
* Share cards were not previewed on real platforms (Facebook/LinkedIn/X validators); tags, dimensions and alt text are checked in the server-rendered HTML.
* Accessibility is verified with axe-core and keyboard E2E only; no screen-reader session.
* Lighthouse numbers vary run to run (several points); INP field data does not exist yet.
* Firefox/Safari and non-Linux platforms (including Windows) untested.
* Turbopack was not re-tested as a production bundler (D-03).
