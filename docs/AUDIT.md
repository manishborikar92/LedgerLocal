# Production-quality audit

Scope: Next.js/Vercel best practices, SEO and social sharing, performance, accessibility, security, content accuracy for a **client-first** app, a full visual redesign, a code-quality pass (v2, 24 October 2026), and the migration to a standard Next.js 16 **server** architecture (this version, 22 November 2026). Evidence tags as in [RESEARCH.md](RESEARCH.md): **[verified]** = measured or run here; **[source]** = taken from a cited page; **[unverified]** = not confirmed.

## 1. Method
Research first (web search), then a baseline review of the v1 code, then changes, each verified with tests, the production build, real-Chromium E2E and Lighthouse. Visual review used screenshots of every key screen in both themes and a phone viewport; it found three layout bugs no test had (§4). The server migration was verified by re-running everything against `next start` and by checking the failure modes it introduced (§4b).

## 3. Content audit (accuracy for a free, client-first tool)
Copy was reviewed so that every claim is true of the product: no unverified third-party claims, only measured numbers (always with the synthetic-data caveat), a visible "Not financial advice" notice. A test fails if app source contains commerce or separate-backend vocabulary, and E2E checks every rendered page for it. Two statements became inaccurate when a Next.js server was introduced and were corrected: the FAQ no longer says there are no servers (it says nothing about your statements ever reaches one), and the verify-offline guide and landing card now name the workbench page (`/app/`) as the one whose policy is `connect-src 'none'`, with the policy read from the response headers rather than the page source. The project is MIT-licensed (D-19).

## 5. Measurements (production build via `next start`, Chrome 153, single-core sandbox) [verified]
**Lighthouse 13.6.0** ([docs/lighthouse.json](lighthouse.json)); median of 3 runs; host benchmark index about 2,500 (see the first bullet for why that matters):
| Page | Perf mobile (slow 4G, 4× CPU) | Perf desktop | A11y | Best practices | SEO | Mobile LCP / TBT / CLS (median) |
|---|---:|---:|---:|---:|---:|---|
| Landing | 90 (runs 90, 94, 90) | 100 | 100 | 100 | 100 | 0.98 s / 407 ms / 0 |
| Guide | 93 (93, 93, 93) | 100 | 100 | 100 | 100 | 0.76 s / 314 ms / 0 |
| Workbench `/app/` | 90 (88, 91, 90) | 100 | 100 | 100 | n/a (`noindex`) | 0.77 s / 419 ms / 0 |
* **Mobile scores depend heavily on the host.** An earlier pass on the same code, with a host benchmark index of about 1,400, gave landing 86, guide 83 and workbench 85 (TBT 0.5–0.7 s). In a back-to-back control on today's host, the build from before the November 2026 dependency update scored 89–94 on the landing page and the updated build 90–94, so the update did not change performance and the difference is the machine. The roughly 90+ target for the workbench is therefore met on this run and was missed on the slower one, with no code change in between. Run-to-run variance is several points.
* The landing page, a server component with a tiny client island, shows about the same Total Blocking Time as the workbench, and the remaining main-thread cost is dominated by the React/Next.js client runtime chunk (about 640 ms scripted at 4× slowdown in one inspected run on the slower host). That is an inference, not a tested cause. The service-worker precache does not appear in the load measurements (it starts after load and idle), and the 1.2 MB pdf.js chunk is not requested at load.
* Lighthouse 12.8 on the same build and Chrome during the slower pass (two runs each, not recorded in the JSON) scored lower: landing 76–77, workbench 77–82. Scores from earlier versions of the app, measured with a different Lighthouse and Chromium, are not comparable and are not reused.
* SEO is 100 on indexable pages. In the earlier build it was 92 because the global `connect-src 'none'` blocked Lighthouse's `robots.txt` audit; only the workbench has that policy now.
**Bundles (gzip)** ([docs/bundle-report.json](bundle-report.json)): landing ≈ 169 KB JS + 9 KB CSS; workbench shell ≈ 212 KB JS; loaded on use: parse worker ≈ 358 KB, PDF renderer ≈ 130 KB, pdf.js render worker ≈ 357 KB. Offline install: 44 files, ≈ 1.4 MB gzip (4.1 MB raw). History: the move to pdf.js's modern build left first-load JS unchanged and cut lazy workbench JS 706 → 672 KB (offline install 1,447 → 1,385 KB gzip); the later pdfjs-dist 6.4.299 → 6.5.438 update added about 1% (672 → 680 KB; offline install 1,395 KB).
**100-page, 4,300-row statement:** file → RECONCILED in ≈ 2.8 s in the browser worker including the first on-demand load of the workbench; max main-thread frame latency 65 ms, 4 long tasks over 50 ms, longest 115 ms ([docs/perf-browser.json](perf-browser.json)); a single run on the faster host state, so not comparable with the 3.5–4.1 s measured earlier on the slower one. Node: 2.2 s extract + 0.43 s parse ([docs/perf-node.json](perf-node.json)).
**Tests:** 163 Vitest (unit, contract, integration incl. `ofxparse`/`openpyxl`/LibreOffice, architecture/CSP/hygiene guards) + 26 Playwright.

## 6. Not verified
* No real Vercel, Render or Coolify deployment was made; `NEXT_PUBLIC_BASE_PATH` sub-path hosting and a reverse proxy in front of the server (Server Action origin check) were not tested. The `?dpl=` deployment-id query that Vercel can add to asset URLs is handled by the service worker (matching ignores the query) but that was not tested on Vercel.
* Share cards were not previewed on real platforms (Facebook/LinkedIn/X validators); tags, dimensions and alt text are checked in the server-rendered HTML.
* Accessibility is verified with axe-core and keyboard E2E only; no screen-reader session.
* Lighthouse numbers vary run to run (several points) and strongly with the host (§5); INP field data does not exist yet.
* Firefox/Safari and non-Linux platforms (including Windows) untested.
* Turbopack was not re-tested as a production bundler (D-03).
* The modern pdf.js build was exercised with the synthetic statements and the bundled samples in Chromium 153 only; the list of required browser features comes from removing each in that browser for the sample statement, and other PDF content might touch more. Firefox and Safari were never run.
